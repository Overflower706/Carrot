조작감 비교 기반 프로젝트 분리 계획

목표. 롤식 · 엘리스식 · 세피리아식 세 조작감을 한자리에서 비교해 볼 수 있는 웹 빌드를 내고, 그 기반 프로젝트를 GitHub에 공개해 다른 기획자·개발자가 받아서 굴려볼 수 있게 한다.
이 문서의 자리. 작업 디렉터리는 C:\Projects\Labs\다 — 원본 CarrotLabs/와 새로 만들 공개 저장소가 나란히 있어야 옮기는 일이 된다.
먼저 읽을 것. 원본 프로젝트의 규약은 CarrotLabs/CLAUDE.md, 지금 진행 중인 작업은 CarrotLabs/Wiki/Plan.html과 Wiki/DevLog08.html에 있다. 이 계획은 그 프로젝트를 건드리지 않는다. 원본은 액션 RTS 2단계를 그대로 계속한다.

1. 왜 「분리」가 아니라 「새 저장소」인가

CarrotLabs의 Assets/는 728MB고, git ls-files 상위가 전부 구매 에셋이다 — Layer Lab(GUI Pro · 2D Minimal-Environment · 2D Minimal-CharacterMaker), Lana Studio VFX, CelerisLab SFX, OccaSoftware, DOTween. 그리고 이것들이 커밋 히스토리 전체에 박혀 있다. HEAD에서 지워도 공개하는 순간 과거 커밋으로 전부 받아진다.

선택지비용위험
git filter-repo로 히스토리 세탁 후 공개 700MB · 수만 파일 대상, 잔여물 확인이 사실상 불가능 하나라도 남으면 라이선스 위반이 공개된 채로 박제된다
새 저장소에 필요한 것만 옮긴다 채택 스크립트 약 25개 + 씬 2개 없음

옮길 양이 세탁 비용보다 명백히 작다. 그래서 새로 판다.

웹 빌드와 소스 공개는 라이선스 기준이 다르다

  • WebGL 빌드 배포 — Unity Asset Store EULA는 빌드된 결과물에 포함하는 것을 허용한다. 원본으로 빌드해도 문제 없다.
  • 소스 공개 — 재배포 금지. 구매 에셋이 전부 빠져야 한다.

여기서 둘로 갈라 관리하고 싶어지지만 공개 저장소 한 곳에서만 뽑는다. 둘을 유지하면 조작 규칙 하나 고칠 때마다 두 번 고쳐야 하고, 조작감 비교에 필요한 그림은 캡슐과 사각형이면 충분하다.

규칙 기반이 싸게 따라오는 이유: RuleDefinition(46줄)은 Resources/Rules에서 에셋만 읽고 인스펙터 배선이 0이며, GameConfigUI(243줄)는 UI를 코드로 생성해서 프리팹·스프라이트 의존이 없다. TMPro만 쓴다. 「규칙 하나 = 에셋 하나 + 씬 하나」라는 구조가 이미 서 있어서 남이 받아서 새 규칙을 붙이는 데 필요한 껍데기는 약 500줄이 전부다.

안 간다

  • 규칙 씬 실물 3종(ActionRTS · BalatroFlow · MassGame) — Combat/ 30여 개 + Unity Behavior 트리 + 구매 VFX/UI에 통째로 엮여 있다. 공개판에는 「조작법 3종 비교」 규칙 하나만 예제로 넣고 나머지는 남이 만들 자리로 비운다. 이것이 「기반 프로젝트」의 정확한 형태다.
  • Combat/ 나머지, Skills/, Character/Skills/, Rules/Lol/, Testing/, _Parked/, Assets/Behaviour/.
  • HexGrid · Parallax · 상점 · 재화 · 요청 시스템 등 규칙 전용 전부.

3. 걷어내야 하는 것 공개 전 필수

  1. Packages/manifest.json의 로컬 패키지 — "com.ovfl.utilities": "file:C:/Projects/Live/_Packages/com.ovfl.utilities". 남이 클론하면 즉시 깨진다. 제거하고, 쓰는 코드가 있으면 인라인한다.
  2. DOTween — CharacterMover, Controls/Lol/LolOrderController, Controls/Sepiria/SepiriaMouseAim이 쓴다. 셋 다 lerp 몇 줄로 대체 가능한 범위로 보인다. 옮길 때 확인할 것.
  3. 캐릭터 프리팹 — Assets/Prefabs/Character/Character_20260707_*.prefab은 Layer Lab CharacterMaker 산출물이다. 캡슐/사각형 + 단색 머티리얼로 새로 만든다. 조작감 비교에는 그림이 오히려 방해다 — 실루엣이 같아야 조작 차이가 보인다.
  4. 폰트 — LINE Seed KR은 재배포 허용 라이선스지만 조건을 확인할 것. 확인이 번거로우면 UI 영문화가 제일 싸다(Unity 기본 LiberationSans로 끝난다).
  5. manifest 정리 — Spine 런타임 3종(코드 참조 0), com.unity.behavior, com.unity.multiplayer.center, com.unity.visualscripting, com.unity.collab-proxy, unity-cli-connector 제거. 남길 것: URP · Cinemachine · Input System · TMP(ugui) · 2D 계열 · test-framework.
  6. AssetUsageDetector는 MIT(yasirkula)라 문제없지만 공개판에 필요 없다. 안 옮긴다.

4. 작업 순서

0단계 · 저장소 이름 정하기 먼저 답할 것

C:\Projects\Labs\ 아래 어떤 이름으로 만들 것인가. CarrotLabs와 나란히 서므로 원본과 헷갈리지 않는 이름이 좋다. 후보: ControlFeelLab · SchemeLab · control-feel-lab. 정해지면 이 문단을 지운다.

1단계 · 빈 프로젝트 + 롤식 하나 여기부터 시작

  • Unity 신규 프로젝트(원본과 같은 에디터 버전). URP 2D Renderer 세팅.
  • manifest를 3장 5번 기준으로 채운다.
  • 2장 「간다」 목록 복사 → DOTween 제거 → 컴파일 통과.
  • 도형 캐릭터 프리팹 하나 + 빈 평지 씬에서 롤식 이동이 돌아가는 것을 눈으로 확인.
  • 여기서 첫 커밋. .gitignore는 원본 것을 그대로 쓴다(Unity 표준 + 검증됨).

이 단계의 판정: 구매 에셋 0인 채로 롤식이 굴러가는가. 안 굴러가면 놓친 의존이 있다는 뜻이다.

2단계 · 규칙 껍데기 완결

  • GameConfig 씬 + 규칙 에셋 1개(ControlComparison, 지원 조작법 셋 다).
  • README.md에 「규칙 추가 = 에셋 하나 + 씬 하나」 절차를 적는다. 이것이 공개의 실체다.
  • LICENSE: 코드 MIT + 「에셋 미포함」 명시.
  • 원본 Assets/Scripts/Controls/README.md와 Rules/README.md도 함께 옮긴다 — 조작법별 분리 원칙 자체가 이 프로젝트가 남에게 주는 것이다.

3단계 · 엘리스식 · 세피리아식 구현 진짜 작업

현재 엘리스식은 ElisMoveController.cs 하나, 세피리아식은 SepiriaMoveController.cs + SepiriaMouseAim.cs뿐이다. 3종 비교라는 결과물 자체가 아직 없다(원본 Wiki/Plan.html도 「조작법 셋 중 롤식만 구현돼 있다」고 적어두고 있다).

반드시 새 저장소에서 만든다. 원본에서 만들면 구매 에셋에 다시 엮이고 나중에 또 떼어내야 한다.

엘리스식 · 세피리아식의 조작 규칙이 어디까지 확정돼 있는지 원본 Wiki에서 확인할 것. Wiki/KeyboardMoveKeyboardSkill_Plan.html, Wiki/KeyboardMoveMouseAttack_Plan.html, Wiki/MouseMoveKeyboardSkill_Plan.html이 관련 문서로 보인다. 미확정이면 임의로 정하지 말고 물어볼 것(CLAUDE.md 개발 원칙).

4단계 · 비교 씬

  • 같은 지형 · 같은 도형 · 같은 목표. 변수는 조작법 하나뿐이어야 비교가 성립한다.
  • 런타임 조작법 전환(재시작 없이). 손에서 손으로 바로 넘어가야 차이가 느껴진다.
  • 화면에 현재 조작법과 키 안내를 상시 표시 — 처음 만지는 사람이 대상이다.

5단계 · WebGL 빌드 + 공개

  • WebGL 빌드 → GitHub Pages(gh-pages 브랜치 또는 /docs).
  • 빌드 산출물은 저장소에 커밋하지 말고 Actions로 뽑거나 별도 브랜치에 둔다.
  • README에 플레이 링크 · 스크린샷 · 「무엇을 비교하는 프로젝트인가」 3줄.

5. 원본과의 관계

  • 원본 CarrotLabs는 비공개로 그대로 유지하고 액션 RTS 2단계를 계속한다.
  • 조작 스크립트가 양쪽에서 갈라지면 공개 저장소가 원본이고 CarrotLabs가 복사본이다. 반대로 하면 옮길 때마다 다시 세탁해야 한다.
  • 공개판에서 개선된 조작 스크립트는 원본으로 복사해 온다. 방향은 항상 공개 → 비공개.

6. 하지 않기로 한 것

  • 히스토리 세탁을 시도하지 않는다. 1장 참조.
  • 빌드용/공개용 저장소를 따로 두지 않는다. 하나에서 뽑는다.
  • 규칙 씬 3종을 옮기지 않는다. 껍데기와 예제 하나면 「갖고 놀 수 있다」는 성립한다.
  • 그림에 시간을 쓰지 않는다. 도형이 오히려 비교에 낫다.
  • 공개 전에 조작법 3종을 다 끝내려 하지 않는다. 1·2단계까지 하고 커밋해두는 편이, 3단계를 비공개로 오래 끌다 한 번에 올리는 것보다 안전하다.
